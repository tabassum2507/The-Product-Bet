An interviewer asked what happens, mechanically, at the moment a load balancer routes a request, not just "it distributes traffic across servers," which was the sentence I had ready, but what it's actually deciding and on what basis. I didn't have a real answer beyond the one-liner, and the one-liner is the kind of thing that sounds like understanding without being understanding.

A load balancer sits in front of multiple servers running identical copies of your application and decides, per incoming request, which server handles it, using some strategy, round robin, sending requests to servers in rotation, least connections, sending to whichever server currently has the fewest active requests, or something smarter that accounts for server health, pulling a server out of rotation entirely if it's failing health checks. The point of all of it is horizontal scaling, instead of buying a single bigger, more expensive machine to handle more load, vertical scaling, you run many smaller, cheaper machines and split traffic across them, which also happens to buy you resilience, one server dying doesn't take the whole system down, the load balancer just stops routing to it.

Where this connects to something I actually understand better, databases don't horizontally scale the same easy way application servers do, and that's a real part of why the SQL versus NoSQL question exists at all, not just a stylistic preference between query languages. A relational, SQL database enforces strong consistency and relationships between tables, which is exactly the property that makes horizontal scaling hard, if data's spread across multiple database servers, keeping every server's view of a joined, consistent dataset in sync in real time is a genuinely difficult coordination problem. NoSQL databases generally trade away some of that strict consistency and relational structure in exchange for being much easier to spread across many servers, which is why they show up so often in systems that need to scale reads and writes horizontally across a lot of load.

That's a real tradeoff, not a strictly-better option in either direction, and it's a product decision as much as an infrastructure one, even though it usually gets framed as purely technical. A billing system probably wants the strong consistency guarantees of a relational database, because a payment being processed twice due to a sync gap is a genuinely bad outcome, worth paying a real scaling cost for correctness. A system logging voice agent call events at high volume can tolerate more relaxed consistency in exchange for being able to write at a much higher rate across many servers, because a slightly delayed or occasionally duplicated log entry is a minor annoyance, not a customer-facing failure.

What I'd actually say in that interview now: a load balancer's job is stateless and comparatively easy, spread requests across identical, swappable servers. A database's job is stateful, and that statefulness is exactly what makes scaling it a real architectural choice, with a real cost, rather than a switch you flip.
